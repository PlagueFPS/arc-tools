# Concrete ingress design review

Unit 4 is accepted and integrated. Unit 3 remains in architecture. The approved product and protocol requirements in `cloudflare-migration-plan.md` remain authoritative.

## Candidate B received

Gemini's candidate `cloudflare-ingress-concrete-design-b-r1` proposes separate admission and execution calls for Twitch, with an opportunistic `waitUntil` execution call backed by a durable alarm. Discord duplicates would poll persisted work until the original execution deadline. Namespace discovery and runtime client resolution follow the accepted account binding pattern.

Root rejects these details before synthesis:

- The proposed Twitch attempt ID `${workId}:${generation}` changes on recovery. After the account sends a reply but before the tenant commits completion, a recovered generation could use a new ID and send again. The account ledger deduplicates only the same complete dispatch input and attempt ID. Freeze the rendered delivery plan before sending; IDs derive from immutable work identity and chunk index, independently of computation generations. Persist that plan before the first dispatch. Recovery reads the same account attempt.
- Scheduling recovery only at the work deadline prevents useful crash recovery within the ten-second window. The alarm must cover the earliest actual next action, including a computation lease expiry or retry time strictly before the original deadline. Admission must persist that alarm before acknowledging.
- FIFO pruning at 64 records could remove a still-live replay tombstone and admit an earlier event again. Bound capacity by rejecting new admission or reclaiming expired records, without shortening the promised replay retention.
- Single concise fixture responses do not prove a maximum for arbitrary validated upstream data. Inspect collection and string bounds and define transport presentation for longer results. Do not truncate silently or assert all outputs fit without proof.
- Storage polling every 50 milliseconds is not established as costless. Compare its bounded work and cancellation behavior with a scoped duplicate join or deterministic terminal fallback. Durable records remain authoritative regardless of any in-memory optimization.

The candidate does not yet resolve the concrete controlled-provider binding through the actual Bot or the Bot callback origin dependency. Those are implementation prerequisites, not user product questions. Candidate A remains active. No synthesis or Unit 3 application implementation is accepted yet.

## Candidate A and preliminary synthesis

Candidate A has now returned. Its smaller public interface exposes `acceptTwitch(receipt)` and `respondDiscord(receipt)`. The tenant owns claims, execution launch, alarms, duplicate waiting, presentation persistence, and recovery. Ingress owns signed bytes and protocol parsing. The account remains the sole owner of credential state and external send attempts; ArcCache remains the sole owner of source freshness. The alarm calls the same tenant recovery operation used by immediate execution.

Root prefers A. Against the six concrete criteria, root scores A/B as follows. Stable dispatch identity scores 5/1; durable admission and useful recovery scores 5/2; Discord deadlines and duplicates scores 4/3; concrete construction and controlled-provider composition scores 4/2; bounded state and replay retention scores 5/1; small public interface and maintenance load scores 4/3. These are design judgments, not runtime measurements. Both candidates converge on transactional claims, network work outside transactions, direct Discord replies, and construction/runtime binding separation. B contributes no additional required mechanism beyond that convergence. Its separate Worker-controlled execution API exposes coordination that A keeps inside the tenant.

The independent cross-judge is active as `cloudflare-ingress-design-crossjudge-r1`. The preliminary choice is not yet an implementation assignment.

## Caller usage and concrete shape

After signature verification and protocol admission, a Twitch raw handler calls `tenants.acceptTwitch(receipt)` and returns 204 only after success. A Discord raw handler calls `tenants.respondDiscord(receipt)` and encodes its public or private initial reply as HTTP 200/type 4. Tenant alarm entry calls `recover()`. Callers do not coordinate claim or delivery phases.

Domain receipts carry a branded tenant key, work identity, invocation, original receipt stamp, and fingerprint. Twitch adds the reply target. Fingerprints cover immutable identity and invocation fields, excluding a retry's newly observed arrival time. Interaction tokens and raw protocol objects never enter tenant storage. The first admitted receipt fixes the deadline. Duplicates cannot extend or rewrite it, including after a delivery plan exists. Conflicting fingerprints fail admission.

One bounded schema-encoded snapshot per tenant owns a work map. Each record is a tagged transport-specific state. Twitch moves through accepted, computing, ready, delivering, and terminal. Discord has computing and terminal states. Claims contain generation, activation identity, and expiry. Pending Twitch records retain only the invocation or immutable presentation plan required by their phase. Terminal Twitch records drop invocation, target, and text. Discord retains its bounded initial response and token-free replay metadata. Tenant identity is fixed and checked at the RPC/storage boundary.

Proposed launch bounds are at most 64 retained records, eight active computations, and 120 KiB encoded state with up to 8 KiB reserved per admitted result. Admission must account for existing encoded bytes plus all outstanding reservations; those maxima cannot all be independently assumed to fit. Expired records can be reclaimed. Capacity pressure rejects new admission rather than evicting unexpired replay records. No periodic maintenance alarm runs on terminal-only tenants.

Twitch admission transactionally stores work, a computation claim, deduplication, and the earliest recovery alarm. The DO registers immediate computation with its own `state.waitUntil` before returning. That registration improves continuity; persisted work and alarm provide recovery. Network work stays outside transactions. Four-second computation leases are an initial bounded policy, never beyond the original ten-second deadline. Alarm selection includes claim expiry and safe retry times, and a bounded batch processes due records. A crash between commit and launch remains recoverable.

Before any dispatch, persist the complete presentation plan, original deadline, exact parent, and deterministic attempt IDs derived from immutable work identity and part index. Computation generations never enter a send-attempt ID. A reconstructed delivering state calls the account with the same complete dispatch input. Success advances the persisted cursor; a retryable outcome schedules only a time before cutoff; rejected, ambiguous, and expired outcomes stop remaining parts. Unknown RPC completion retains the same attempt for recovery. Fencing suppresses stale tenant completion but cannot promise exactly-once external delivery.

Discord execution stays attached to the original request. The first request owns an atomic computation claim. Duplicates read the recorded result or wait with bounded storage reads until its original cutoff. A waiter can transactionally commit the common private timeout and fence computation; a reconstructed active claim becomes a private interrupted-request result. No alarm or later callback delivers Discord replies. An in-memory optimization is unnecessary for this launch, and storage polling is not free. Bound both read count and time.

Candidate A proposes receipt plus 2,350 milliseconds for command computation and 2,700 milliseconds for the tenant RPC response, within the original three-second response budget. These are hypotheses to measure, not verified headroom. Timestamp at the start of Worker fetch before client resolution, route construction, or body consumption. If tenant RPC fails or exhausts its budget after a valid Discord request, the Worker returns a deterministic friendly private initial failure while time remains. This fallback does not claim a committed tenant result. A lost concurrent response can differ; there is no later token POST or background message to duplicate. Storage failures remain observable. Do not let a late result overwrite a committed timeout or silently extend a deadline.

Ingress reads a bounded raw stream, initially 64 KiB, with a body-read timeout. Verify original bytes before JSON decoding, with freshness and bounded future skew. Check Twitch type/version/condition, resolved permitted broadcaster, and command syntax before tenant lookup. Ordinary chat and unknown commands create no tenant work. Challenges remain pending; notifications and revocations use the actual verifier callback/client/signing context through `subscriptionBinding`. Await revocation persistence before acknowledgement. Discord verifies application, command, guild/member and guild-install context. PING needs no guild. No DM tenant, guild enrollment, or allowlist is added.

Presentation preserves command strings and stale provenance. Freeze deterministic Twitch parts within the provider limit, including labels, with stable part IDs; ambiguity stops remaining parts. Generated parts cannot parse as commands, allowing personal-sender commands without recursion. Proposed maximum is eight parts. If the complete result cannot fit the bounded plan, return an explicit bounded size failure rather than truncate. Discord returns public success or an explicit private size/error result within 2,000 content characters, suppressing mentions. Existing short fixtures do not prove arbitrary results fit. Verify provider counting and Unicode handling before accepting formatting.

## Construction and cloud proof

`worker.ts` owns composition and receipt stamping, `api.ts` raw route definitions, `ingress.ts` protocol verification/parsing, `tenant.ts` state ownership and DO/RPC adaptation, and `presentation.ts` pure formatting. A small Discord adapter owns initial-response encoding. Avoid unnecessary forwarding modules or public wire types.

Add `bindData` analogous to `bindAccount`. Namespace discovery runs during construction; a returned Effect resolves `RuntimeContext` and the environment client at runtime. Tenant construction binds account and data once and provides their services to operations. `bindTenants` follows the same split. No storage or provider I/O runs during planning. Root verified that pinned Alchemy exposes `Cloudflare.Worker.URL` as a deferred accessor and `DurableObjectState.waitUntil` as an Effect accepting the caller context. Their existence does not yet prove the proposed complete wiring.

Use the deferred self-URL binding to derive one actual Bot origin for callback, redirect, and verification binding, without reading `Bot.url` from its dependency graph. A configured public URL must match the deployed origin. Cloud tests must exercise actual Bot routes and Tenant with production cache/account policy and controlled external API Workers. A test-only composition module may supply validated synthetic-stage endpoint bindings, rejected for personal and production stages. Keep fixture controls under `tests/cloud`; expose no production control routes. Replace the invalid synthetic Discord public key with a valid test Ed25519 pair.

Extend the existing 15 canonical cases. Track every added Worker and namespace and verify full teardown. Local Alchemy Bun tests prove transitions, stale completion, deadlines, duplicate responses, quotas, payload cleanup, presentation and recursion behavior. Cloud tests prove signed bytes, no allocation on rejected ingress, admission/alarm persistence before 204, reconstruction, native recovery, controlled sends and retries, ambiguity, real cache access, public/private payloads, and the full cold response path. Report actual timings and headroom without equating controlled fixtures with live provider timing or cost. Preserve terminal business failures and narrowly classified readiness retries.
